# 콘텐츠 검수

## 원칙
**확인하지 못한 문장은 남기지 않는다.** 판정은 합격과 불합격 둘뿐이다. "보류", "조건부 합격", "대체로 괜찮음"은 없다.

검수는 두 가지를 다 한다. 하나는 **절차 점검**(출처, 사실, 표절, 정책)이고, 하나는 **독자로서 끝까지 읽기**(약속과 내용이 맞는지)다. 절차에서 일찍 불합격이 정해져도 끝까지 읽고 찾은 것을 모두 보고한다. 그래야 고치는 사람이 한 번에 고친다.

검수할 때는 글을 쓴 기억으로 확인하지 않는다. 출처를 다시 열어서 본다. 같은 대화에서 방금 쓴 글이라도 마찬가지다.

검수자는 본문을 고칠 수 있지만 **출처를 새로 만들지 않는다**. 출처가 모자라면 불합격으로 보고하고, 출처를 모으는 일은 `ebook-production` 스킬 2단계로 돌려보낸다.

## 시작 전에 읽는다
1. `CLAUDE.md`의 "왜 돈을 내는가", "내용 규칙"
2. `docs/writing-style.md` 7장(금지·주의 표현)

## 1단계. 대상을 정한다
| 대상 | 본문 | 출처 목록 | 출처 본문 보관 |
|---|---|---|---|
| 전자책 | `src/books/<slug>/book.json` (+ `chapters/*.md`) | `src/books/<slug>/sources.md` | `.research/<slug>/*.txt` |
| 칼럼 등 글 한 편 | `<글>.md` | `<글>.sources.md` | `.research/<파일이름>/*.txt` |

출처 목록(`sources.md`)은 이 표 형식이다. 열 이름을 바꾸지 않는다.

```markdown
| # | 종류 | 제목 | 주소 | 확인일 | 무엇을 확인했나 |
|---|---|---|---|---|---|
| 1 | 공식 문서 | 프로젝트 만들기 | https://support.example.com/projects | 2026-11-10 | 프로젝트 메뉴 위치, 무료 요금제에서 되는지 |
| 2 | 강의 | ○○ 입문 3강 | https://example.org/course/3 | 2026-11-10 | 초보자가 막히는 지점 |
| 3 | 글 | △△ 사용 후기 | https://blog.example.net/post | 2026-11-10 | 실제 사용 순서 |
```

- 종류는 `공식 문서`, `강의`, `영상`, `글`, `기사`, `논문` 중 하나로 쓴다. 도구를 만든 회사가 낸 문서만 `공식 문서`다.
- 확인일은 그 주소를 실제로 연 날짜다.
- 출처 본문은 출처를 읽을 때마다 글자만 뽑아 `.research/<이름>/<번호>-<사이트>.txt`로 저장한다. 이 폴더는 저장소에 올라가지 않는다.

## 2단계. 자동 검사를 돌린다
명령 하나가 문체·구조·상세페이지 검사까지 모두 돌리고 `reviews/<이름>-<날짜>.md` 보고서를 만든다.

```bash
node scripts/review-prep.mjs --book <slug>
```
글 한 편이면 `node scripts/review-prep.mjs --file <글.md> --type column`(긴 글형 챕터는 `--type deep`)이다.

- 이후 단계의 결과는 모두 이 보고서에 적는다.
- 본문을 고친 뒤 같은 명령을 다시 돌리면 보고서의 1번(자동 검사)만 새로 쓰인다. 나머지는 그대로 남는다.
- △(주의)는 불합격이 아니지만 하나씩 읽고, 고칠 수 있으면 고친다.

## 3단계. 독자처럼 끝까지 읽는다
첫 장부터 마지막 장까지 순서대로 읽는다. 보고서 2번 표의 항목마다 **맞음 / 어긋남**과 근거가 되는 장 번호를 적는다. "어긋남"이 하나라도 있으면 불합격이다.

| 볼 것 | 어긋남의 예 |
|---|---|
| 제목·부제·칩의 약속이 본문에서 이뤄지는가 | 부제는 "한 번에 만들어요"인데 본문은 10일치씩 세 번 나눠 요청한다 |
| 숫자가 서로 같은가 | 상세페이지는 "입력값 6개", 본문에서 세면 5개 |
| 입력값의 `[ ]`마다 무엇을 넣을지 알려주는가 | `[목표]`가 있는데 본문과 예시 어디에도 목표를 정하는 장이 없다 |
| 앞 장을 가리키는 말이 맞는가 | "위 3가지 주제"라고 했는데 앞 장의 결과는 콘셉트 3가지다 |
| 확인 방법이나 막혔을 때 할 일이 있는가 | 표를 받으라고만 하고, 글로 나왔을 때 할 일이 없다 |
| 요약이 실제로 만든 것인가 | 요약에 "해시태그 묶음"이 있는데 해시태그 장이 없다 |
| 다음편 소개가 이어지는가 | "오늘 만든 계정에 올릴 상세페이지"처럼 앞뒤가 맞지 않는 소개 |
| 상세페이지 문구가 본문과 맞는가 | 상세페이지는 "30분", 표지 칩은 "1시간" |

`CLAUDE.md`의 "왜 돈을 내는가" 넷 중 셋을 갖췄는지도 여기서 본다. 갖춘 것과 그 근거가 되는 장 번호를 보고서 6번에 적는다. 셋이 안 되면 불합격이다.

## 4단계. 사실을 확인한다
보고서 3번 표에 확인이 필요한 문장이 들어 있다. 표에 없더라도 도구 이름, 메뉴 이름, 버튼 이름, 요금, 수치, 날짜, 순위, 인용이 나오면 줄을 추가한다.

문장마다 아래 순서로 처리한다.
1. 장 수, 입력값 수처럼 책 자체에서 세어 확인하는 것은 직접 세고, 맞으면 **확인**, 출처 칸에 "책 데이터"라고 적는다.
2. 그 밖의 문장은 출처 목록에서 뒷받침하는 출처를 찾아 주소를 연다.
3. 출처에 그 내용이 있으면 **확인**이라고 쓰고 출처 번호를 적는다.
4. 출처와 다르면 본문을 출처대로 고치고 **고침**이라고 쓴다. 메모에 무엇을 바꿨는지 적는다.
5. 뒷받침하는 출처를 찾지 못하면 본문에서 그 문장을 지우거나 사실 주장이 없는 문장으로 바꾸고 **삭제**라고 쓴다.
6. 주소를 열 수 없으면(로그인 필요, 웹을 쓸 수 없음) 판정 칸을 비워 두고 메모에 이유를 적는다. 빈 줄이 남으면 불합격이다.

| 본문 문장 | 상황 | 나쁜 처리 | 좋은 처리 |
|---|---|---|---|
| "무료 계정으로 하루 30번까지 쓸 수 있어요." | 공식 문서에 횟수가 없다 | 그럴듯하니 "확인"으로 적는다 | **삭제**. "무료 계정으로 시작할 수 있어요. 사용량 한도는 공식 안내를 확인하세요."로 바꾸고, 무료로 시작할 수 있다는 것도 출처로 확인한다 |
| "왼쪽 위 '새 대화' 버튼을 눌러요." | 공식 문서의 버튼 이름이 "새 채팅"이다 | 뜻이 같으니 둔다 | **고침**. 화면에 보이는 이름 그대로 쓴다 |
| "마케터의 70%가 AI를 써요." | 출처가 블로그 글 하나이고 원 조사를 못 찾았다 | 블로그를 출처로 적고 "확인" | **삭제**. 원 조사를 찾지 못한 수치는 쓰지 않는다 |
| "한 번에 10일치씩 요청해요." | 수치가 있지만 따라 할 방법이다 | 표에서 그냥 지운다 | **확인**으로 두고 메모에 "사실 주장 아님, 따라 할 방법"이라고 적는다. 효과를 수치로 약속하는 문장이면 삭제한다 |
| "2026년 11월 10일에 확인한 내용이에요." | 그날 출처를 연 기록이 없다 | 문서에 적힌 날짜를 옮겨 적는다 | **고침**. 출처 목록의 확인일로 바꾼다. 확인일이 없으면 삭제한다 |

## 5단계. 출처 기준을 본다
앞의 셋은 `review-prep`이 본다. 넷째는 직접 본다.
- 서로 다른 사이트 3곳 이상
- 전자책이면 종류가 `공식 문서`인 출처 1개 이상. 글 한 편이면 도구 사용법을 다룰 때만 필요하다
- 모든 출처에 확인일이 있고, 확인일이 책의 작성 시점보다 30일 넘게 앞서지 않는다
- 출처 하나에만 나오는 내용이 본문의 절반을 넘지 않는다

## 6단계. 표절을 점검한다
1. **통째로 같은 문장**: `review-prep`이 12자 이상인 문장이 출처와 똑같으면 불합격으로 잡는다. 입력값 박스도 본다. 도구의 메뉴 이름만으로 된 문장이 걸렸으면 보고서 5번에 그 사유를 적고, 그 밖에는 모두 고쳐 쓴다.
2. **같은 긴 구절**: 30자 이상 같으면 불합격, 20자 이상은 모두 고쳐 쓴다.
3. **구성**: 보고서 5번 표에 출처마다 목차를 적는다. 우리 목차와 같은 순서로 이어지는 항목이 우리 항목 수의 절반 이상이면 불합격이다.
4. **예시**: 출처에 나온 예시, 비유, 프롬프트 문구, 사례 속 가상의 가게 이름을 그대로 쓰지 않았는지 본다. 하나라도 있으면 우리 예시로 바꾼다.

## 7단계. 정책을 점검한다
보고서 4번의 항목을 하나씩 본문에서 찾아 확인하고 체크한다. 이미지 항목은 이미지 파일을 실제로 열어 보고 체크한다. 체크하지 못한 항목이 있으면 불합격이다.

## 8단계. 판정한다
아래 중 하나라도 해당하면 **불합격**이다. 모두 해당하지 않을 때만 **합격**이다.
- 자동 검사(보고서 1번)에 ✗가 하나라도 있다
- 본문 통독 표에 "어긋남"이 있거나 빈 줄이 있다
- 사실 확인 표에 판정이 빈 줄이 있다
- "삭제"로 적었는데 본문에 그 문장이 남아 있다
- 5단계 출처 기준을 하나라도 못 채웠다
- 6단계에서 불합격 조건에 걸렸다
- 7단계에 체크하지 못한 항목이 있다
- "왜 돈을 내는가" 넷 중 셋을 갖추지 못했다

본문을 고쳤으면 2단계 명령을 다시 돌리고, 새로 쓰인 자동 검사 결과로 판정한다.

## 9단계. 보고한다
사용자에게는 이 순서로 알린다.
1. 판정 (합격 또는 불합격)
2. 불합격이면 걸린 항목 전부와 고쳐야 할 것
3. 고친 문장 수, 삭제한 문장 수 (0이어도 적는다)
4. 확인하지 못한 것 (예: 로그인이 필요해 열지 못한 출처)
5. 보고서 파일 위치

## 이런 생각이 들면 멈춘다
| 드는 생각 | 실제로 해야 할 일 |
|---|---|
| 출처가 없으니 불합격으로 끝내면 된다 | 3단계 통독과 7단계 정책 점검까지 하고 찾은 것을 모두 보고한다 |
| 수치가 상식적이니 출처 없이 둬도 된다 | 출처가 없으면 삭제한다 |
| 방금 내가 조사해서 쓴 글이라 다시 볼 필요가 없다 | 출처를 다시 연다 |
| 출처가 2곳뿐이지만 둘 다 믿을 만하다 | 불합격으로 보고한다. 검수자가 출처를 지어 넣지 않는다 |
| 검사기 기준이 너무 엄격하다 | 기준을 바꾸지 않는다. 바꿔야 한다고 생각하면 사용자에게 묻는다 |
| 조금만 고치면 되니 합격으로 적는다 | 고친 뒤 검사를 다시 돌리고 그 결과로 판정한다 |
| 수정하면 될 것 같으니 "보류"로 적는다 | 판정은 합격과 불합격뿐이다. 고칠 것은 불합격 사유로 적는다 |
