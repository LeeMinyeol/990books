# 상세페이지 제작

## 원칙
상세페이지는 **살지 말지 정하는 데 필요한 사실을 순서대로 보여주는 곳**이다. 설득은 과장이 아니라 결과물, 들어 있는 것, 앞 3장 미리보기로 한다.

책마다 페이지를 새로 디자인하지 않는다. 정해진 블록을 고르고 순서를 정해 `book.json`의 `detail`에 데이터로 넣는다. 완성 예시는 `src/books/insta-month/book.json`의 `detail`이다. 타입은 `src/lib/book.ts`의 `DetailSpec`이다.

상세페이지 화면(블록을 그리는 코드)은 아직 구현 전이다. 이 스킬은 데이터까지만 만든다. 화면에서 확인할 수 없다는 것을 보고에 적는다.

## 시작 전에 읽는다
1. 책의 `src/books/<slug>/brief.md`(주제 카드)와 `book.json`
2. `docs/writing-style.md` 5-3, 7장
3. `docs/reference-ebooks.md` (가져올 것과 가져오지 않을 것)

## 0단계. 책이 준비됐는지 본다
책의 준비물 장이나 본문에 "확인 필요", "미정" 같은 표시가 남아 있으면 상세페이지를 만들지 않는다. `ebook-production` 스킬의 2단계와 6단계로 돌아가 먼저 채운다. `detail-check`도 이 경우 불합격으로 잡는다.

## 1단계. 틀을 고른다
위에서부터 차례로 보고, 처음 맞는 줄의 틀을 쓴다.

| 순서 | 조건 | 틀 |
|---|---|---|
| 1 | `kind`가 `deep`이다 | D 심화 가이드 |
| 2 | 주제 카드의 "막힌 곳"이 독자가 이미 해 보다 실패한 장면이다 (예: "광고를 켰는데 문의가 없다") | B 문제 해결 중심 |
| 3 | 주제 카드의 "그 도구를 처음 쓰는 독자인가"가 "예"다 | C 도구 입문 중심 |
| 4 | 그 밖 (결과물이 눈에 보이는 것이다) | A 결과물 중심 |

주제 카드에 판단할 정보가 없으면 지어내지 말고 사용자에게 묻는다.

틀마다 블록 순서는 정해져 있다. 괄호 친 블록은 조건이 맞을 때만 넣고, 괄호 없는 블록은 빠질 수 없다(`detail-check`가 본다).

| 틀 | 블록 순서 |
|---|---|
| A | hero → outcome → includes → steps → preview → toc → (before-after) → facts → faq → refund → (reviews) → (next) |
| B | hero → for-whom → problem → before-after → includes → preview → toc → facts → faq → refund → (reviews) → (next) |
| C | hero → steps → includes → for-whom → preview → toc → facts → faq → refund → (reviews) → (next) |
| D | hero → for-whom → toc → includes → preview → (before-after) → (problem) → facts → faq → refund → (reviews) → (next) |

블록은 모두 8~11개다. `reviews`는 승인된 후기가 3개 이상일 때만, `next`는 이어지는 책이 공개돼 있을 때만 넣는다.

## 2단계. hero 모양을 고른다
| 조건 | 모양 |
|---|---|
| 표지 이미지가 표·달력·문서처럼 가로로 넓다 | `stack` (이미지 위, 글 아래) |
| 표지 이미지가 없거나, 용어·글 중심의 책이다 | `band` (포인트컬러 바탕에 제목) |
| 그 밖 | `split` (글 왼쪽, 이미지 오른쪽) |

그다음 같은 분야에서 바로 앞에 만든 책을 본다. "같은 분야"는 `book.json`의 `category`가 같은 책이고, "바로 앞"은 준비물 장의 작성 시점이 가장 가까운 앞선 책이다. 그런 책이 없으면 넘기지 않는다. **틀과 hero 모양이 둘 다 같으면** hero 모양을 `split → stack → band → split` 순서로 하나 넘긴다. 책마다 느낌이 달라지게 하는 장치다.

## 3단계. 색을 확인한다
색은 책의 `accent`를 쓴다. 고르는 규칙은 `ebook-production` 스킬 5단계에 있다. 여기서는 확인만 한다.
- `src/lib/palette.json`에 있는 색인가
- `onAccent`가 목록의 값과 같은가
- 같은 분야의 다른 책과 겹치지 않는가

상세페이지에서 포인트컬러는 hero(band일 때 바탕), 버튼, 체크 표시, 소제목 옆 표시에만 쓴다. 본문 글자색으로 쓰지 않는다.

## 4단계. 블록 문구를 쓴다
`toc`, `preview`, `facts`, `refund`, `reviews`는 화면이 책 데이터에서 내용을 만든다. 제목(`title`)만 쓴다.

| 블록 | 무엇을 보여주나 | 쓰는 것 | 기준 |
|---|---|---|---|
| `hero` (필수) | 표지, 제목, 가격, 버튼 | `variant`, `lead` | 소개문 2~3문장, 160자 이하 |
| `outcome` | 완성 결과물 | 제목, 이미지, 설명 | 설명 60자 이하. 도구 화면이 아니라 결과물 |
| `includes` (필수) | 들어 있는 것 | 제목, 항목 2~5개 | 이름 20자, 설명 60자 이하. 개수를 숫자로 |
| `for-whom` | 이런 상황이라면 | 제목, 항목 3~5개 | 항목당 40자 이하. 독자가 겪는 장면 |
| `problem` | 왜 막히는지 | 제목, 본문 | 200자 이하. 독자 탓으로 쓰지 않는다 |
| `before-after` | 따라 하기 전과 후 | 제목, 전, 후 | 각 80자 이하. 눈에 보이는 차이 |
| `steps` | 만드는 순서 | 제목, 단계 2~5개 | 이름은 동작, 설명 60자 이하 |
| `toc` (필수) | 전체 목차와 분량 | 제목 | |
| `preview` (필수) | 앞 3장 그대로 | 제목 | 요약으로 대신하지 않는다 |
| `faq` | 자주 묻는 질문 | 제목, 질문 3~5개 | 질문은 "?"로 끝, 답 140자 이하 |
| `facts` (필수) | 작성 시점, 도구, 버전, 분량 | 제목 | |
| `refund` (필수) | 환불 안내 | 제목 | 문구는 화면에 고정돼 있다 |
| `reviews` | 완독자 후기 | 제목 | 3개 이상일 때만 |
| `next` | 이어지는 책 | 제목 | |

블록 제목은 4~24자이고, 그 블록이 말하는 것을 문장으로 쓴다("다 따라 하면 이런 계획표가 생겨요").

- 버튼 문구는 화면에 고정돼 있다("앞 3장 무료로 보기", "전체 보기"와 가격). 책마다 쓰지 않는다.
- `includes`에는 독자가 받는 것(슬라이드, 입력값, 파일)만 넣는다. 다 따라 하면 생기는 결과물은 `outcome`이나 `before-after`에 넣는다.
- 문구에 "슬라이드 N장", "입력값 N개"를 쓰면 `book.json`에서 센 실제 값과 같아야 한다(`detail-check`가 본다). 입력값은 `label`이 "입력값 N"인 박스만 센다.

### hero 소개문 공식: 장면 → 원인 → 주는 것
| | 예 |
|---|---|
| 나쁜 예 | 인스타그램 마케팅의 모든 것을 담은 완벽 가이드! 누구나 쉽게 따라 하면 팔로워가 폭발적으로 늘어납니다. 지금 바로 시작하세요! |
| 좋은 예 | 한 달 치 게시물을 그날그날 정하면 금방 지쳐요. 주제와 순서를 먼저 정해 두면 쓰는 일만 남아요. 이 책은 30일 계획표와 캡션, 해시태그를 차례로 만드는 순서를 담았어요. |
| 이유 | 첫 문장은 독자가 겪는 장면, 둘째는 막히는 원인을 다시 본 것, 셋째는 책에 들어 있는 것이다. 약속하는 것은 결과물뿐이고, 본문이 실제로 하는 방식과 같은 말로 쓴다 |

### for-whom: 사람의 종류가 아니라 겪는 장면
| 나쁜 예 | 좋은 예 |
|---|---|
| 인스타그램 초보자 | 저녁마다 "오늘 뭐 올리지"로 30분을 쓴다 |
| 마케팅에 관심 있는 분 | 계정은 만들었는데 게시물이 3개에서 멈췄다 |
| 성공하고 싶은 사장님 | 올릴 때마다 말투와 주제가 달라진다 |

### includes: 형용사가 아니라 개수와 쓰임
| 나쁜 예 | 좋은 예 |
|---|---|
| 알찬 프롬프트 모음 — 실전에서 바로 쓰는 노하우 | 복사해 쓰는 입력값 5개 — 클로드에 순서대로 붙여넣어요. 바꿀 곳은 [ ]로 표시했어요. |

### faq: 사기 전에 실제로 걸리는 것
아래에서 책에 해당하는 것을 3~5개 고른다. 답은 책 데이터와 `CLAUDE.md`에서 확인되는 사실만 쓴다.
- PDF로 받을 수 있나요? → 사이트에서만 볼 수 있고, 결제한 뒤에는 계속 볼 수 있다
- 유료 요금제가 필요한가요? → 준비물 장에 적힌 그대로
- 얼마나 걸리나요? → `minutes`와 장 수
- 도구가 바뀌면 책도 바뀌나요? → 고쳐 준다고 약속하지 않는다. 작성 시점과 버전을 책에 적어 둔다
- 처음 써 보는데 따라 할 수 있나요? → 준비물 장의 내용으로 답한다
- 환불되나요? → 열람 전에는 되고, 열람을 시작한 뒤에는 안 된다

## 쓰지 않는 것
`detail-check`가 불합격으로 잡는다.
- 긴급성 장치: 마감 임박, 남은 자리·수량, 오늘만, 선착순, 가격 인상 예고
- 근거를 댈 수 없는 배지: 1위, 베스트셀러, 필독서, 상위 N%, 누적 판매 N권
- 부풀린 정가: "정가", "N% 할인", "N원 상당"
- 수익·성공 약속, 수익 금액
- "여러분", "무조건", "누구나 쉽게", "인생을 바꾸는"
- 이모지
- "확인 필요", "미정" 같은 채우지 않은 자리
- 지어낸 후기, 지어낸 저자 경력 (후기는 `reviews` 블록이 실제 데이터로만 보여준다)

## 5단계. 검사한다
```bash
node scripts/detail-check.mjs <slug>
npx tsc --noEmit
```
✗가 0개가 될 때까지 고친다. 그다음 직접 본다.
- [ ] hero 소개문의 세 문장이 각각 장면, 원인, 주는 것인가
- [ ] 걸리는 시간과 그 밖의 숫자가 `book.json`의 실제 값과 같은가 (장 수와 입력값 수는 검사기가 본다)
- [ ] "한 번에", "자동으로" 같은 말이 본문이 실제로 하는 방식과 맞는가
- [ ] faq의 답이 책 데이터나 `CLAUDE.md`로 확인되는가
- [ ] 같은 분야의 직전 책과 블록 순서나 hero 모양이 다른가
- [ ] 문구가 다른 책의 상세페이지와 문장 단위로 겹치지 않는가

## 6단계. 보고한다
- 고른 틀과 hero 모양, 그렇게 고른 조건 한 줄
- 블록 순서
- 검사 결과
- 화면 구현 전이라 눈으로 확인하지 못했다는 것
